## 一、内存层级（Memory Hierarchy）

```
寄存器 → L1 → L2 → L3 → RAM → SSD → HDD
 1ns   0.5ns  7ns  30ns  100ns  0.1ms  10ms
```

| 概念 | 要点 | 数据库关联 |
|------|------|-----------|
| 虚拟内存 | 页表、TLB、缺页中断 | Buffer Pool = 用户态页表，管理磁盘页↔内存帧 |
| 内存页 Page | OS 4KB，数据库更大（8K/16K） | 数据库 I/O 最小单位 |
| TLB | 页表缓存，miss 代价高 | huge page 减少 TLB miss |
| Cache Line | 64 字节，CPU 一次拉取单位 | 行存储快（记录在 1-2 个 cache line），列存储字段分散 |
| NUMA | 多 socket 内存不对称 | **物理事实不是开关**；`numactl --interleave=all` 均匀分配 buffer pool |
| mmap | 文件映射到虚拟地址空间 | MongoDB 早期、RocksDB 可选；OS 代管缓存不可控 |
| O_DIRECT | 绕过 OS 页缓存 | 数据库倾向自己管理 buffer pool |

### 核心纠正（常见混淆）
- **Page Cache ≠ Buffer Pool**：两套独立缓存。OS 管 Page Cache，数据库管 Buffer Pool。可共存（双重缓存浪费内存），可用 O_DIRECT 跳过
- **数据库 Page ≠ OS 内存 Page**：16KB vs 4KB，TLB 管的是地址映射不是数据
- **NUMA 不是可开启的优化**：是硬件物理事实
- **mmap 不是通用 I/O**：特定系统调用，Page Fault 由内存访问触发

### 完整数据流（磁盘→CPU 四层）
```
Layer 0 磁盘    扇区 512B/4KB；HDD 随机~10ms；SSD 随机~0.1ms
Layer 1 OS 内核  VFS / Page Cache / 页表 / MMU / 缺页处理
Layer 2 数据库   Buffer Pool / WAL / 锁 / B+树 / MVCC
Layer 3 CPU      TLB / L1-L3 / NUMA / Cache Line 64B
```

## 二、数据结构基础（数据库视角）

### 数组
连续内存，`arr[i] = 起始地址 + i × 元素大小` O(1)。中间插入/删除 O(n)。动态数组（Go slice）均摊 O(1)。

### 链表
散落内存靠指针串联。头部插入 O(1)。**缓存不友好**（遍历比数组慢 10-50 倍）→ 数据库索引用 B+ 树而非二叉树的原因之一。

### 栈 / 队列
LIFO / FIFO。应用：函数调用、撤销、BFS、消息队列、Redo Log 环形队列。

### 哈希表
`hash(key) → 数组下标`，O(1)。冲突解决：拉链法（Java HashMap）/ 开放地址法（Python dict）。负载因子 0.75 触发扩容 rehash。**不支持范围查询**。

### B+ 树（重点）
- 多路搜索树，树高 3-4 层 → 磁盘 I/O 次数极少
- 内节点只存 key + 指针；叶子节点存数据 + 双向链表（范围查询）
- 聚簇索引（叶子存整行）vs 二级索引（叶子存主键，需回表）
- 每个节点 = 一个 16KB page ≈ 1000 个 key → 2000 万行树高仅 3
- 分裂（Split）：中间分裂 50:50，可级联至根；合并（Merge）：利用率低时合并，InnoDB 倾向不主动合并

### LSM-Tree
```
写入 → MemTable(跳表/红黑树,内存) → 满则 flush → SSTable(磁盘,有序)
      → Compaction 合并去重
```
- 写优化（顺序写）vs 读放大（多层查找）；B+ 树相反（随机写慢、读快）
- Compaction 策略：Leveled（RocksDB 默认，写放大~70x）/ Tiered（Cassandra，写放大小读放大）
- 布隆过滤器：快速判断"肯定不存在"，减少无效 I/O

### 跳表（Skip List）
概率平衡，实现简单，支持范围查询，并发友好。Redis ZSet、RocksDB MemTable 使用。

### 选型决策树
```
精确匹配某个值   → 哈希表 O(1)
范围查询         → 内存:红黑树/跳表；磁盘:B+树
Top K           → 堆
前缀/模糊匹配    → Trie
FIFO/LIFO       → 队列/栈
高频写入+偶尔查  → LSM-Tree
```

## 三、持久化文件存储系统

### 磁盘物理层
- **HDD**：寻道(~8ms) + 旋转(~4ms) ≈ 随机 I/O 10ms；顺序比随机快 100 倍
- **SSD**：随机读 ~0.1ms；**不能直接覆盖**（按页写 4KB、按块删除 256KB）→ 写放大
- NVMe 多队列：64K 并发队列，多线程 I/O 才能喂饱

### 文件系统
- inode = 文件身份证（元数据 + 数据块指针），文件名在 dentry 不在 inode
- 多级索引：12 直接指针(48KB) + 一级间接(4MB) + 二级(4GB) + 三级(4TB)

### 三种 I/O 路径
| | buffered | O_DIRECT | mmap |
|---|----------|----------|------|
| 缓存控制 | OS | 数据库 | OS |
| 拷贝次数 | 2 | 1 | 按需 |
| 数据库偏好 | ❌双重缓存 | ✅首选 | ⚠️MongoDB 早期 |

### WAL（Write-Ahead Logging）
**改数据页之前，先把"怎么改的"记到 Redo Log。提交 = Redo Log 落盘。**

```
修改数据 → 写 Redo Log Buffer → COMMIT: fsync Redo Log(顺序写) → 成功
→ 后台慢慢刷脏页(随机写) → Checkpoint 推进可覆盖 LSN
```
快 100 倍：提交只 fsync 1 次顺序日志 vs N 次随机数据页。崩溃恢复 = 重放 Redo Log。

### Double Write（双写缓冲区）
防**页撕裂**（16KB 页写一半断电，前新后旧，checksum 坏）。

```
Step1: 脏页批量顺序写双写区(2MB 连续区域) → 安全
Step2: 各页分散写回原位置 → 撕裂时从双写区取副本恢复
```

### WAL vs Double Write
| | WAL | Double Write |
|---|-----|--------------|
| 解决 | 已提交事务断电丢失 | 数据页物理撕裂 |
| 发生在 | 每次 COMMIT | 脏页刷盘时 |
| 能否关 | 不能（ACID 的 D） | 可关（SSD 原子写） |

> WAL 保证事情记下来了（内容不丢），Double Write 保证纸没撕坏（载体不坏）。

### Checkpoint
标记"LSN=N 之前的数据页已全部刷盘"→ Redo Log 可覆盖。Fuzzy（InnoDB，增量平滑）vs Sharp（全量，I/O 洪峰）。

## 四、数据库引擎详解

### 定义
**引擎 = 数据库内部真正干活的那套代码，负责存储、检索、事务管理。SQL 是统一接口，引擎是实现。**

### 四大子系统
1. **查询引擎**：SQL 解析 → AST → 优化器 → 执行器
   - 迭代器模型（Volcano）：open/next/close 三方法，流水线拉式执行
   - JOIN 算法：Nested Loop O(n²) / Index Nested Loop O(n log n) / Hash Join O(n+m)（等值） / Merge Join O(n+m)（已排序）
   - 外部排序：归并段 + 多路归并；哈希聚合 O(n) 优于排序聚合
2. **存储引擎**：数据怎么存怎么读。InnoDB 层次：表空间→段→区(1MB/64页)→页(16KB)
   - 行格式 COMPACT：变长长度列表 + NULL 位图 + 记录头 + 列数据 + 隐藏列(trx_id/roll_ptr)
   - 页目录：页内稀疏索引，二分查找 O(log n)
   - 列存：同列连续，压缩率极高（字典编码+RLE）
3. **事务引擎**：ACID 守护者
   - 原子性=Undo Log，持久性=Redo Log，隔离性=锁+MVCC
   - 隔离级别：READ UNCOMMITTED < READ COMMITTED < REPEATABLE READ（InnoDB 默认，Next-Key Lock 防幻读）< SERIALIZABLE
   - MVCC：Undo Log 版本链 + Read View 快照；写不阻塞读
   - 锁：S/X 兼容矩阵、意向锁、Next-Key Lock = 记录锁 + 间隙锁
   - ARIES 恢复：Analysis → Redo（重演历史）→ Undo（回滚未提交）
4. **缓冲引擎**：Buffer Pool 管理
   - LRU 改良：中点插入（热端 5/8 + 冷端 3/8），防全表扫描冲垮缓存
   - 预读（Read-Ahead）：线性/随机；写合并（Group Commit）：多个事务一次 fsync

### 引擎对比
| | InnoDB | MyISAM | RocksDB |
|---|--------|--------|---------|
| 存储 | B+树行式 | B+树行式 | LSM-Tree |
| 事务 | ✅ | ❌ | ✅ |
| 锁 | 行锁 | 表锁 | 行锁 |
| 写性能 | 中 | 中 | 极高（5-10x） |
| 读性能 | 极快 | 快 | 中（多层查找） |

## 五、MySQL 表连接（SQL 层）

- **INNER JOIN**：两边都有才要
- **LEFT JOIN**：左表全保留，右表无则 NULL（ON 条件不影响左表保留，WHERE 才是最终过滤器）
- **RIGHT JOIN**：与 LEFT 对偶，少用
- **FULL OUTER JOIN**：MySQL 不直接支持，UNION 模拟
- **CROSS JOIN**：笛卡尔积，危险
- **SELF JOIN**：自己连自己，别名区分
- 执行顺序：FROM+JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
- 实际执行：Nested Loop（驱动表选过滤后行数少的）/ Block Nested Loop（join buffer）/ Hash Join（8.0.18+）
- EXPLAIN 关注：type（ALL<index<range<ref）、rows、Extra（Using index/join buffer/temporary）

---

## 一句话总结

> 引擎的原理，就是**在四个独立问题上的最优解**：怎么执行最快（迭代器）、怎么存最省（B+Tree/LSM）、怎么并发出错最少（MVCC+锁）、怎么用内存加速 I/O（Buffer Pool+WAL）。四个解拼在一起，就是你现在用的数据库。
